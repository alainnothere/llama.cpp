# Why `restic`, not Syncthing or rsync

## Syncthing is not a backup

Syncthing is a **sync** tool. That means:

- if a file is deleted on one side, it may be deleted on the other
- it is not primarily designed for long-term versioned retention
- it can be great for live mirroring an “incoming photos” folder, but it is not the right tool as your main photo backup

If you later want Syncthing, use it only for a narrow job, like syncing a camera/phone import folder, and **do not let it propagate deletions from untrusted machines into your main library**.

## rsync is a mirror, not a backup

`rsync` over SSH is useful, but as a backup strategy it has problems:

- no encryption at rest by default
- no real versioning unless you build it yourself
- a bad flag or bad script can overwrite/delete your only copy
- you end up maintaining more custom logic than you need

`restic` gives you the backup behavior you actually want:

- encrypted
- deduplicated
- incremental
- snapshot/versioned
- easy to schedule
- works over SFTP/SSH
- can verify and restore

# The concrete stack

## 1. Use WireGuard between your home and your sister’s place

If her NAS or router can run WireGuard, do that.

Example:

- private subnet: `10.200.0.0/24`
- sister’s NAS: `10.200.0.2`
- your home server: `10.200.0.1`

Then your home server talks to the NAS over the private WireGuard IP.

If her NAS/router cannot run WireGuard, your next-best option is:

- SSH/SFTP with key-only auth
- strict firewall rules
- no password auth

But **WireGuard is the cleaner answer** if she can run it.

### Offsite repo on sister’s NAS

- user: `backup`

Do not use her admin account. Give it write access only to the backup path.

That is the machine that runs the backup job.

You do **not** need to run a special restic server on the NAS.

```bash
restic init \
  --repo sftp:backup@192.168.1.50:/backup/restic-local \
  --key-file /etc/restic/local.key \
  --password-file /etc/restic/local.password
```

```bash
restic init \
  --repo sftp:backup@10.200.0.2:/volume1/restic-offsite \
  --key-file /etc/restic/offsite.key \
  --password-file /etc/restic/offsite.password
```

### Important key rules

- **Do not put the key files on sister’s NAS.**
- **Do not put the key files on the old laptop either**, if you want maximum paranoia.
- Keep the key/password files:
  - on the home server for normal operation
  - and in at least one **offline** copy
- If you lose the key, the backups are effectively unrecoverable.

That last part is the whole privacy tradeoff:

- if your sister gets the repo, she still cannot read it
- if you lose the key, you cannot read it either

So the key is sacred.

For the “memes folder” problem: this is exactly why `restic` is a good answer.  
It encrypts file names too, so the repo does not just say “encrypted contents”; it does not even expose the original folder/file names in plain text.

# 5. Run the backups

A simple backup script on the home server:

```bash
#!/usr/bin/env bash
set -euo pipefail

backup_repo() {
  local repo="$1"
  local key="$2"
  local pass="$3"

  RESTIC_REPOSITORY="$repo" \
  RESTIC_KEY_FILE="$key" \
  RESTIC_PASSWORD_FILE="$pass" \
  restic backup /photos --tag photos

  RESTIC_REPOSITORY="$repo" \
  RESTIC_KEY_FILE="$key" \
  RESTIC_PASSWORD_FILE="$pass" \
  restic forget \
    --keep-daily 7 \
    --keep-weekly 4 \
    --keep-monthly 12
}

# Local backup
backup_repo \
  "sftp:backup@192.168.1.50:/backup/restic-local" \
  /etc/restic/local.key \
  /etc/restic/local.password

# Offsite backup
backup_repo \
  "sftp:backup@10.200.0.2:/volume1/restic-offsite" \
  /etc/restic/offsite.key \
  /etc/restic/offsite.password
```

Then run it on a schedule, e.g. daily:

```cron
0 3 * * * /usr/local/bin/restic-backup.sh
```

If you want to reclaim disk space more aggressively, add a **weekly prune**:

```bash
RESTIC_REPOSITORY="$repo" \
RESTIC_KEY_FILE="$key" \
RESTIC_PASSWORD_FILE="$pass" \
restic forget --prune
```

You do not necessarily need to prune daily.  
Daily backup + weekly prune is a sane default.

Rework the plan by **inverting the tunnel direction**.

Do **not** try to port-forward into your sister’s CGNAT connection.

## New concrete plan

Assuming your home connection can accept one inbound connection — port-forwarded IPv4 or usable IPv6 — do this:

```text
[Sister NAS behind CGNAT]
        |
        | outbound-only WireGuard client
        v
[Your home server = WireGuard server]
        |
        | restic over private WireGuard IP
        v
[Sister NAS SFTP repo]
```

Your backup topology stays the same:

```text
[Home server /photos]
   ├── local restic backup on old laptop / USB SSD
   └── offsite restic backup on sister’s NAS
```

But now the offsite link works despite her CGNAT because **she calls you**, not the other way around.

---

# 1. Make your home server the WireGuard endpoint

On your home server:

- install WireGuard
- assign it a private tunnel IP, e.g. `10.200.0.1/24`
- expose one UDP port to the internet, e.g. `51820`
- if your home IP changes, use free DDNS
- if you have IPv6, you may not need port forwarding at all

Example home/server side concept:

```ini
[Interface]
PrivateKey = <home-server-private-key>
Address = 10.200.0.1/24

[Peer]
# Sister’s NAS
PublicKey = <nas-public-key>
PresharedKey = <psk>
AllowedIPs = 10.200.0.2/32
```

On your home router:

- forward UDP `51820` to your home server  
  **or**
- if using IPv6, allow inbound UDP to the home server’s IPv6 address

That is the only inbound piece you need.

---

# 2. Make her NAS a WireGuard client

On her NAS:

- install/enable WireGuard client mode
- set the endpoint to your home server’s public IP or DDNS name
- assign it a private tunnel IP, e.g. `10.200.0.2/24`
- set it to start automatically and keep reconnecting

Example NAS/client side concept:

```ini
[Interface]
PrivateKey = <nas-private-key>
Address = 10.200.0.2/24

[Peer]
PublicKey = <home-server-public-key>
PresharedKey = <psk>
Endpoint = your-home.ddns.example:51820
AllowedIPs = 10.200.0.0/24
PersistentKeepalive = 25
```

That `PersistentKeepalive = 25` is useful because she is behind NAT/CGNAT.

### Why this works with CGNAT

CGNAT blocks inbound connections to her side.  
It does **not** block outbound connections from her side.

So this works:

- her NAS → your home server

And once the tunnel is up, this also works:

- your home server → her NAS over `10.200.0.2`

No port forwarding on her side.  
No UPnP.  
No DMZ.  
No exposed SFTP port.

---

# 3. Keep SFTP private to the tunnel

On her NAS:

- enable SFTP
- create a dedicated `backup` user
- give it write access only to the backup path
- firewall it so SFTP is accepted **only from `10.200.0.1`**

That last part matters.  
You do not want SFTP reachable from the public internet just because the tunnel exists.

---

# 4. Restic stays almost exactly the same

On your home server, your offsite repo now looks like this:

```bash
restic backup /photos \
  --repo sftp:backup@10.200.0.2:/volume1/restic-offsite \
  --key-file /etc/restic/offsite.key \
  --password-file /etc/restic/offsite.password \
  --tag photos
```

Your local repo stays the same:

```bash
restic backup /photos \
  --repo sftp:backup@192.168.1.50:/backup/restic-local \
  --key-file /etc/restic/local.key \
  --password-file /etc/restic/local.password \
  --tag photos
```

or, if you use a USB SSD locally:

```bash
restic backup /photos \
  --repo /mnt/usb-ssd/restic-local \
  --key-file /etc/restic/local.key \
  --password-file /etc/restic/local.password \
  --tag photos
```

Everything else from the previous plan still applies:

- encrypted repos
- external key files
- versioning
- retention policy
- restore tests

# 5. Adjust expectations for the offsite copy

Because she is now abroad and behind CGNAT, the offsite copy is still valid, but it is now a **cold offsite copy**, not a fast local-ish one.

That means:

- first full backup may be slow
- restores from her NAS may be slow
- the backup job is now dependent on:
  - her NAS being powered on
  - her internet working
  - the WireGuard tunnel staying connected
  - her bandwidth not being capped or terrible

So operationally:

- keep your **local backup** as the fast, reliable restore source
- treat the sister NAS as the **offsite safety copy**
- if the tunnel is down, the local backup should still succeed

A sane schedule is:

- local backup: daily
- offsite backup: daily if the link is good, otherwise weekly

If her connection is bad, do not force a huge daily offsite backup.  
Make the offsite copy less frequent but still real.

---

# 6. If her NAS cannot run WireGuard client

Some NAS boxes are easier than others.

If her NAS can run a WireGuard client, use that.

If it cannot, the next-best no-cloud option is an **outbound SSH reverse tunnel** from her NAS to your home server.

The idea is the same:

- her NAS initiates SSH to your home server
- that SSH session creates a private tunnel back to her NAS
- your home server then talks to her NAS through that tunnel

This also requires your home side to be reachable, but it avoids needing WireGuard on the NAS.

I would still prefer WireGuard if the NAS supports it, because it is cleaner and more robust.

---

# 7. What if your home side also cannot accept inbound?

This is the important caveat.

The plan above assumes **your home side is reachable** in at least one of these ways:

- port-forwarded IPv4
- usable IPv6

If your home ISP is also CGNAT and you cannot accept inbound connections either, then a purely self-hosted, no-cloud, always-on tunnel between the two sites gets much harder.

In that case, the honest answer is:

- you still keep the local `restic` backup
- but a continuous offsite backup to her NAS without some reachable endpoint or relay is not really feasible

If you absolutely refuse any cloud/relay service, then the no-cloud rework becomes:

```text
[Home server /photos]
   ├── local restic backup on old laptop / USB SSD
   └── offline encrypted restic backup on a USB drive you physically store elsewhere
```

That is the boring, reliable, no-cloud fallback.

You would:

- keep one encrypted restic repo on a USB drive
- store that drive in another physical location
- rotate/refresh it periodically

It is less automatic than a network offsite copy, but it still satisfies the core goal:

- encrypted
- offsite
- no cloud
- no paid service

# Bottom line

With her CGNAT, the reworked plan is:

1. **Your home server becomes the WireGuard server.**
2. **Her NAS becomes an outbound WireGuard client to your home server.**
3. **Restic runs from your home server to her NAS over the private tunnel IP.**
4. **Local backup stays local.**
5. **Her NAS becomes a slower, colder offsite copy.**

If your home side is reachable, that is the clean answer.

If your home side is **also** unreachable and you will not use any relay/cloud service at all, then replace the network offsite copy with an **offline encrypted restic drive** you physically store somewhere else.

# 1. How long the initial online seed would take

Your upload speed is the bottleneck.

Assume:

- photo library: **800GB**
- upload: **5 Mbps**
- `restic` over SFTP/WireGuard
- photos are mostly JPEGs, so do **not** expect much compression savings

## Idealized math

800GB = 6400Gbit

At a perfect 5Mbps:

```text
6400Gbit / 5Mbps = 1280 hours
1280 hours / 24 = 53.3 days
```

So even in fantasy-land, the first backup is **about 53 days**.

## Real-world math

Real throughput will be lower because of:

- TCP/SFTP overhead
- WireGuard overhead
- WAN latency
- retries
- router/NAS limitations
- incomplete pipe utilization

A reasonable planning number is **70–85%** of raw upload.

# 3. Should you seed onto a disk and mail it?

**Yes.**

For your numbers, this is clearly the better plan.

## Why physical seeding wins

### Online seed
- cost: ~$0
- time: **2.5–3.5 months**
- risk: long tail of failures, caps, instability

### Physical seed
- cost: one external drive + shipping
- time: **days to a couple of weeks**
- risk: much lower
- after that, online backups are small

A **2TB external USB SSD** is the right tool.

Why 2TB?

Because your repo will start near **800GB**, and you do not want to be one bad estimate away from running out of space.

A 1TB drive *might* fit depending on whether you mean 800GB vs 800GiB and how much overhead you have, but I would not plan around it.

**Use 2TB.**

# 5. Exact local seeding steps

Assume:

- photos are in `/photos`
- USB drive is `/dev/sdb`
- you will use an ext4 partition on the drive
- the repo directory on the drive will be `/restic-offsite`

## Format the drive

```bash
sudo mkfs.ext4 -L seed /dev/sdb1
sudo mkdir -p /mnt/seed
sudo mount /dev/sdb1 /mnt/seed
sudo mkdir -p /mnt/seed/restic-offsite
```

## Initialize the seed repo

Use the **same offsite key** you will later use for the NAS repo.

```bash
restic init \
  --repo /mnt/seed/restic-offsite \
  --key-file /etc/restic/offsite.key \
  --password-file /etc/restic/offsite.password
```

## Run the seed backup

```bash
restic backup /photos \
  --repo /mnt/seed/restic-offsite \
  --key-file /etc/restic/offsite.key \
  --password-file /etc/restic/offsite.password \
  --tag seed
```

## Set your retention policy

For example:

```bash
restic forget \
  --repo /mnt/seed/restic-offsite \
  --key-file /etc/restic/offsite.key \
  --password-file /etc/restic/offsite.password \
  --keep-daily 7 \
  --keep-weekly 4 \
  --keep-monthly 12
```

## Verify locally before shipping

At minimum:

```bash
restic check \
  --repo /mnt/seed/restic-offsite \
  --key-file /etc/restic/offsite.key \
  --password-file /etc/restic/offsite.password
```

And do a small restore test:

```bash
restic restore latest \
  --repo /mnt/seed/restic-offsite \
  --key-file /etc/restic/offsite.key \
  --password-file /etc/restic/offsite.password \
  /tmp/seed-restore-test
```

If that works, unmount cleanly:

```bash
sudo umount /mnt/seed
```

# 7. What your sister needs to do

This is where simplicity matters.

## If she is comfortable with NAS storage

Give her a drive like this:

- ext4
- one folder: `restic-offsite`

Her job:

1. plug the drive in
2. mount it
3. copy the `restic-offsite` folder to the NAS
4. make sure the NAS backup user can read/write it
5. tell you when done

Example target path on her NAS:

```text

```

Important:

- **do not rename the repo files**
- **just copy the existing repo directory**

The repo is already initialized. You are moving the repo, not creating a new one.

## Permissions note

After she copies it, the NAS backup user needs write access to the repo directory.

On many NAS boxes that means something like:

```bash
chown -R backup:backup /volume1/restic-offsite
chmod -R u+rwX,g+rwX,o-rwx /volume1/restic-offsite
```

Exact commands depend on the NAS OS.

# 10. Shipping the drive

Yes, mail it.

## Practical details

Use:

- tracked shipping
- insurance
- normal consumer external drive
- good packaging

## Security

The drive contains a `restic` repo, so:

- file contents are encrypted
- file names are encrypted
- the key is not on the drive

So if the drive is lost or stolen, that is not a direct data breach.

## Border / customs caveat

If this is an international shipment, be aware that encrypted media can sometimes attract extra attention at borders. Laws vary a lot by country.

I’m not giving legal advice, but the practical points are:

- know the rules in both countries
- do not label the drive in a way that invites scrutiny
- understand that refusing to provide a key can have legal consequences in some jurisdictions

For most people, a normal encrypted backup drive is fine, but you should be aware of the risk.
